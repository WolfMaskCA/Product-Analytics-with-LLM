# Product Analytics with LLM — the number, and the conversation around it

A single self-contained page that shows one product metric twice: first as a standard
event-analytics tool reports it, then as an interactive dashboard that says where you
stand, what to change, and what the change did. Same underlying events both times.

The scenario: a subscription fitness app converts 24.9% of free trials to paid. The
standard view can tell you that. It cannot tell you whether it is good, what to change,
or whether the change worked — and that gap is what the second view fills.

**All data is synthetic.** "Generic Fitness App" is not a real company. Every install,
trial and conversion — and the industry ranges too — is generated by a seeded script.
The industry context is illustrative and directional, not a published benchmark.

---

## What the page does

**The switch at the top is the transition.** "Standard analytics view" is the default.
Click "Interactive dashboard" and a vertical line travels across the full width of the
content area, replacing one view with the other as it goes.

**View 1 — standard analytics.** Funnel, weekly trend, volume, summary table, under
fake tool chrome. It ends deliberately short, on a two-column panel listing what it can
and cannot answer, and the observation that the next step is someone exporting this to
a slide where the analysis immediately starts drifting from the data.

**View 2 — the same events, staged for the three people who need them:**

| Stage | Audience | What it carries |
|---|---|---|
| **1 · Where we are** | Analyst | The rate plotted against the typical industry range by trial length, with a "you are here" pin. Then the diagnosis: 55% of cancellations land on day zero. Ends in a one-paragraph hypothesis. |
| **2 · What we propose** | Developer | Exactly two changes. Each states why, the change, **where** (the actual config key), what we expect — and shows the before/after screen or flow. |
| **3 · What happened** | Stakeholder | Result tiles, the weekly trend against a dotted "where we started" line, the stage-1 range chart again with the arms marked on it, and guard metrics that check the win is not hollow. Ends in a recommendation. |

Two changes, not four: a longer trial, and a paywall shown after onboarding rather than
on first launch. Any more and it stops being a recommendation and starts being a backlog.

## The argument it makes

A chart tool plus a written analysis puts the number in one system and its meaning in
another. The interpretation is written once, at one moment, and ages from then on; a
developer reads a paragraph and infers the change; six weeks later nobody can reconstruct
why the change was made. Putting the benchmark, the diagnosis, the proposal and the
result on the same data keeps the reasoning attached to the number — and it updates when
the data does.

## How it's built

1. **Bring an outside anchor to the number** — a metric with nothing to compare it to
   cannot be acted on. The benchmark strip is what turns "24.9%" into a position.
2. **Tag the free text with a local model** — where a project has open-ended input
   (support messages, cancellation reasons, call transcripts), a local LLM turns it into a
   fixed label set. High volume, low stakes, no per-token cost, nothing leaves the machine.
3. **One atomic cube** — `cube[arm][week] = {installs, trials, paid, cancels, renewed}`.
   Every panel is derived from it, in Python at build time and again in JavaScript on
   filter, so two panels cannot disagree.
4. **Self-verify at build** — the generator re-derives each view two ways and refuses to
   publish on a mismatch.
5. **One self-contained file** — no server, no database, no chart library. Charts are
   hand-drawn SVG; data is inlined.

## Build

Python 3, stdlib only. No dependencies, no virtualenv.

```bash
python3 scripts/build_demo_data.py      # -> data/demo_data.json   (seeded, deterministic)
python3 scripts/build_page.py           # -> index.html            (self-contained)
open index.html                         # plain file — no server needed
```

Verify without writing anything:

```bash
python3 scripts/build_demo_data.py --check   # cube reconciles to every derived view
python3 scripts/build_page.py --check        # page carries its synthetic-data disclosure
```

`build_page.py` refuses to write if the data is not flagged synthetic, or if the output
contains any token from the private project this method was developed in.

## Layout

```
scripts/build_demo_data.py   the synthetic dataset + the cube + the self-checks
scripts/build_page.py        inlines the data into the template
src/template.html            the page: styles, SVG chart primitives, panels
data/demo_data.json          generated — do not hand-edit
index.html                   generated — the published artifact
```

## Notes on the charts

- No dual-axis plots, and no truncated y-axis on the results chart — the arms are compared
  from zero, with a dotted reference line for where we started, because the tiles can carry
  the magnitude without the axis exaggerating it.
- The categorical palette is validated for colour-vision separation against both the light
  and dark surface before shipping, rather than picked by eye.
- Every series is direct-labelled and every chart has a table view, so identity never rests
  on colour alone. Overlapping direct labels are pushed apart and tied back with a leader.
- Light and dark are both selected palettes, not an automatic inversion.
